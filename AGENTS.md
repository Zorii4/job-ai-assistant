# Инструкции для coding-агентов

## Назначение и область действия

Этот файл задаёт публичные правила работы для всего репозитория. Он должен быть
самодостаточным в clean clone. Если локально есть
`local/internal-docs/AGENTS.private.md`, прочитайте его после этого файла: это ignored
private-дополнение владельца, которое не требуется для сборки и не должно попадать в Git.

Перед значимой задачей прочитайте:

1. этот `AGENTS.md`;
2. [README.md](README.md) и относящиеся публичные документы из `docs/`;
3. `local/internal-docs/AGENTS.private.md` и документы, на которые оно ссылается, только
   если эта private-директория уже доступна в рабочей копии.

Не ищите и не пытайтесь восстановить отсутствующие private-материалы, secrets,
production prompts или реальные evaluation-данные.

## Контекст проекта

Job AI Assistant — portfolio-проект, развивающийся из TypeScript Telegram-бота в
web-приложение для работы кандидата с резюме и конкретной вакансией. Язык текущего MVP
интерфейса — русский.

Существующий initial AI workflow сохраняет порядок:

```text
Analyst
  -> Producer
  -> Critic
  -> Producer revision при необходимости
  -> Orchestrator
```

Он создаёт черновики для ручной проверки пользователя. Приложение не отправляет отклики,
письма или сообщения и не изменяет внешние профили от имени пользователя.

Текущая и целевая архитектура описаны в [docs/architecture.md](docs/architecture.md),
а продуктовый scope — в [docs/product-spec.md](docs/product-spec.md). Не выдавайте
планируемые компоненты за реализованные.

## Базовые инварианты

- Не меняйте порядок, смысл и контракт initial AI workflow без отдельной задачи и
  регрессионных проверок.
- Не смешивайте в одном изменении архитектурный рефакторинг, production prompts, модель
  и формат финального результата.
- New AI scenarios проектируйте как отдельные workflows, а не как неявное расширение
  существующего Producer.
- AI создаёт только черновики; внешние действия всегда остаются ручным решением человека.
- Проверки владения данными выполняются на сервере, а не через скрытые элементы UI.
- Внешние данные валидируются runtime-схемами; TypeScript assertion не заменяет валидацию.

## Приватность и безопасность

- Исходный текст резюме не передаётся в LLM. Для будущего AI-использования пользователь
  подтверждает отдельную обезличенную версию.
- Не логируйте пользовательские тексты, prompt-тексты, LLM raw responses с пользовательским
  содержимым, cookies, auth headers, tokens или ключи.
- Не добавляйте в Git production prompts, реальные резюме, вакансии, заметки, результаты
  AI, fixtures с реальными данными или evaluation corpus.
- Не выполняйте реальные платные LLM-вызовы без явной задачи и понимания стоимости.
- Для файлов и пользовательского ввода учитывайте ownership, IDOR, XSS, CSRF, path
  traversal, oversized input и prompt injection.

Подробнее: [docs/privacy-and-security.md](docs/privacy-and-security.md) и
[SECURITY.md](SECURITY.md).

## Граница публичных материалов

Каждый новый файл должен иметь явную классификацию в
[`public-file-policy.json`](public-file-policy.json): `PUBLIC`, `PRIVATE`, `SECRET` или
`GENERATED`. Не классифицированный tracked-файл считается запрещённым до решения
владельца.

При появлении нового пути или рискованной категории:

1. предложите владельцу классификацию до добавления в Git;
2. после решения обновите policy, `.gitignore` и scanner, если он нужен;
3. обновите затронутые публичные документы в той же задаче.

Перед commit запускайте:

```sh
npm run check:public-safety
```

Для hook один раз настройте:

```sh
git config core.hooksPath .githooks
```

`.gitignore` не заменяет scanner и ручной review. Не обходите ignore через `git add -f`.

## Работа над задачей

1. Изучите затронутый код, тесты и документацию.
2. Сформулируйте инварианты и короткий план одной проверяемой итерации.
3. Сделайте минимальное изменение, не расширяя scope попутно.
4. Добавьте или обновите тесты пропорционально риску.
5. Запустите релевантные проверки, просмотрите diff и обновите документацию при изменении
   публичного поведения, архитектуры, статуса функции или security/privacy границы.
6. В результате перечислите собственные изменения, проверки и оставшиеся риски.

При новой странице, layout или визуальном редизайне используйте локальный визуальный
процесс проекта; принципы текущего интерфейса описаны в
[docs/design-system.md](docs/design-system.md).

## Тесты и качество

Минимальный набор проверок выбирается по типу работы:

- backend: validation, ownership, happy path и error path;
- background job: success, retry, duplicate delivery, quota и отсутствие дубликатов;
- AI-контракт: валидный и невалидный fixture, отсутствующее поле и релевантные запреты;
- frontend: loading, empty, error, success, сохранение и доступность основного действия.

Тесты по умолчанию не обращаются к реальной LLM. Перед завершением используйте
релевантные команды, например `npm test`, `npm run build`, `npm run build:api`,
`npm run build:web`, `npm run prisma:validate` и `npm run check:public-safety`.

## Рабочая директория и зависимости

Рабочая директория может содержать незавершённые изменения другого участника. До
редактирования проверяйте `git status` и относящийся diff; не перезаписывайте чужие
изменения, не используйте `git reset --hard` или `git checkout --`, не удаляйте
неизвестные файлы.

Перед добавлением зависимости убедитесь, что существующий стек не решает задачу,
изучите официальную документацию и не добавляйте несколько библиотек с одной ролью.
Не меняйте package manager и не выполняйте массовое обновление зависимостей попутно.

## Когда остановиться и спросить владельца

Запросите решение до продолжения, если требуется изменить семантику AI workflow,
выбрать несовместимую миграцию или риск потери данных, подключить внешний сервис с
персональными данными или платой, изменить квоты/продуктовую единицу, выполнить внешнее
действие, выйти за публичный scope либо раскрыть закрытый материал.

Во всех остальных случаях выбирайте минимальное безопасное решение в рамках этой
документации и фиксируйте допущения в результате.
